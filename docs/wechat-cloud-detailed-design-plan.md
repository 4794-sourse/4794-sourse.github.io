# 基于微信云开发的详细设计计划（V1）

## 1. 目标与范围

### 1.1 产品目标
- 基于现有站点能力，补齐后端数据与业务能力，实现“可运营、可观测、可扩展”的应用架构。
- 后端统一采用**微信云开发（CloudBase）**，减少自建运维成本，提升上线效率。
- 第一阶段聚焦核心闭环：用户登录、内容数据管理、互动行为（评论/点赞/收藏）、基础运营后台。

### 1.2 业务范围（V1）
- C 端：
  - 微信登录与用户档案初始化。
  - 内容列表、详情、搜索。
  - 评论发布/回复、点赞、收藏。
- 管理端：
  - 内容审核（评论审核、违规词处理）。
  - 内容管理（新增、编辑、上下架）。
  - 运营看板（DAU、内容阅读、互动转化）。
- 非目标（V1 暂不做）：
  - 复杂推荐算法。
  - 多租户隔离。
  - 跨云部署。

---

## 2. 技术架构设计

### 2.1 总体架构
- 前端：Web/H5（现有站点）+ 可扩展小程序端。
- 接入层：微信云托管/静态托管 + 云函数 API。
- 业务层：云函数（Node.js）实现鉴权、业务逻辑、聚合查询。
- 数据层：云数据库（集合模型）+ 云存储（媒体资源）。
- 能力层：云调用（订阅消息/安全内容检测）、定时触发器、日志与监控。

### 2.2 架构原则
- **无状态函数**：业务状态存数据库，函数可水平扩展。
- **最小权限**：按函数分配数据库/存储权限。
- **幂等优先**：互动类接口（点赞、收藏）采用幂等设计。
- **可观测性内建**：每个函数统一日志字段（traceId、uid、耗时、错误码）。

### 2.3 环境规划
- `dev`：开发联调环境。
- `staging`：预发布回归环境。
- `prod`：生产环境。
- 环境变量统一配置：第三方密钥、开关项、限流阈值等。

## 3. 数据模型设计（云数据库）

### 3.1 集合清单
1. `users`
2. `posts`
3. `comments`
4. `likes`
5. `favorites`
6. `audit_logs`
7. `metrics_daily`

### 3.2 核心字段建议

#### users
- `_id`：用户唯一 ID（可用 openid 映射）
- `openid`、`unionid`（如可用）
- `nickName`、`avatarUrl`
- `role`：`user | admin | super_admin`
- `status`：`active | banned`
- `createdAt`、`updatedAt`

索引建议：
- `openid` 唯一索引
- `role + status` 组合索引

#### posts
- `_id`
- `title`、`summary`、`content`
- `coverUrl`、`tags[]`
- `status`：`draft | published | offline`
- `authorId`
- `stats`：`viewCount`、`likeCount`、`commentCount`、`favoriteCount`
- `publishedAt`、`createdAt`、`updatedAt`

索引建议：
- `status + publishedAt`
- `tags`
- `authorId + createdAt`

#### comments
- `_id`
- `postId`
- `userId`
- `content`
- `parentId`（回复评论）
- `status`：`pending | approved | rejected`
- `createdAt`、`updatedAt`

索引建议：
- `postId + createdAt`
- `userId + createdAt`
- `status + createdAt`

#### likes / favorites
- `_id`
- `postId`
- `userId`
- `createdAt`

索引建议：
- `userId + postId` 唯一索引（防重复）
- `postId + createdAt`

## 4. 接口与云函数设计

### 4.1 函数拆分
- `auth-login`：校验登录态、初始化用户。
- `post-list`：分页查询内容。
- `post-detail`：内容详情 + 计数更新。
- `comment-create`：评论发布（含敏感内容检测）。
- `comment-list`：评论列表。
- `interaction-like-toggle`：点赞/取消点赞。
- `interaction-favorite-toggle`：收藏/取消收藏。
- `admin-post-upsert`：后台内容新增/编辑。
- `admin-comment-audit`：评论审核。
- `metrics-daily-job`：定时聚合统计。

### 4.2 统一返回协议
- 成功：`{ code: 0, message: 'ok', data: {...}, traceId }`
- 失败：`{ code: <业务错误码>, message: <错误信息>, traceId }`

### 4.3 关键业务规则
- 点赞/收藏采用 toggle，但以数据库唯一键保证幂等。
- 评论创建必须经过安全检测，不通过进入 `rejected`。
- 内容下线后，详情接口返回“不可见”状态，不暴露正文。

---

## 5. 权限与安全设计

### 5.1 角色权限
- 普通用户：读公开内容、发评论、点赞收藏。
- 管理员：内容管理、评论审核、查看运营数据。
- 超级管理员：管理员权限分配、高危操作。

### 5.2 安全策略
- 所有写接口必须校验登录态和角色。
- 高频接口增加限流（按 uid + IP）。
- 评论/昵称等用户输入做 XSS 过滤。
- 媒体资源采用临时授权 URL，避免长期裸链。
- 审计日志记录管理操作（操作者、时间、变更前后）。

## 6. 性能与稳定性

### 6.1 性能目标（SLO）
- 95 线接口响应：< 300ms（缓存命中）
- 99 线接口响应：< 800ms
- 可用性：>= 99.9%

### 6.2 优化手段
- 热点内容详情使用云缓存（短 TTL）。
- 列表接口使用“游标分页”避免深分页性能衰减。
- 聚合计数异步化（写操作先入队，定时对账修正）。

### 6.3 容灾策略
- 关键集合每日备份。
- 云函数错误重试 + 死信记录。
- 监控报警：错误率、超时率、调用量突增。

---

## 7. 运维与监控

### 7.1 可观测性
- 统一日志字段：`traceId`、`uid`、`funcName`、`latency`、`code`。
- 建立看板：
  - 接口成功率、P95/P99。
  - 关键路径转化（登录->浏览->互动）。
  - 内容审核积压量。

### 7.2 发布流程
1. 开发分支联调（dev）
2. 自动化测试通过
3. 发布 staging 验收
4. 灰度发布 prod（10% -> 50% -> 100%）
5. 回滚预案（函数版本回滚 + 配置回滚）

---

## 8. 迭代计划与里程碑

### 8.1 阶段划分
- **M1（1~2 周）**：
  - 完成数据模型、登录、内容查询接口。
  - 打通前后端联调与基础日志。
- **M2（1~2 周）**：
  - 评论、点赞、收藏闭环。
  - 评论审核与管理端基础能力。
- **M3（1 周）**：
  - 统计任务、监控看板、告警。
  - 性能压测与上线准备。

### 8.2 验收标准
- 关键接口通过率 > 99%。
- 评论审核链路可用，误拦截率可量化。
- 线上告警与回滚机制可演练。

---

## 9. 风险清单与应对

1. **云函数冷启动导致抖动**
   - 预热关键函数、优化依赖体积、提高并发配置。
2. **内容安全误判影响用户体验**
   - 采用“机器初审 + 人工复核”策略。
3. **数据统计口径不一致**
   - 统一指标字典，日报任务固定口径出数。
4. **突发流量冲击**
   - 限流、缓存、降级（关闭非核心接口）。
